### UI Patterns — Responsive/Duplication Risk

- `src/app/admin/vehicles/page.tsx` renders its per-row "⋮" action menu (edit/delete/etc.) in two separate places in the JSX: once for the mobile card view (~line 1618) and once for the desktop table view (~line 1735+, shifts with edits). - [2026-08-30, RESOLVED same session] **The desktop table's "⋮" action-menu dropdown (`styles.actionMenu`, `position:absolute`) was getting clipped/cut off by `styles.tableContainer`'s border** — user reported with a screenshot + arrow pointing at a half-visible menu button. Root cause: `tableContainer` has `overflowX:'auto'` (needed for the 800px-min-width table to scroll horizontally on narrow screens) — per the CSS overflow spec, setting `overflow-x` to anything but `visible` forces `overflow-y` to compute as `auto` too, so any absolutely-positioned descendant that would render outside the container's box (like the dropdown opening from the last/rightmost — visually leftmost in RTL — "פעולות" column) gets clipped by that same box, regardless of the dropdown's own `zIndex`. **Fixed only the desktop table's menu** via `createPortal(..., document.body)` with position computed from the "⋮" button's `getBoundingClientRect()` at click time (new `actionMenuPos` state) — this moves the dropdown out of the clipped DOM subtree entirely, which `zIndex` alone can never do since z-index doesn't escape a clipping ancestor. **The mobile card view's identical-looking menu (`styles.cardList`) was deliberately left untouched** — confirmed it has no `overflow` ancestor, so it isn't actually clipped; portaling it too would be defensive-only, not a real fix, so skipped per "don't fix what isn't broken." **General lesson for this codebase: `overflow-x: auto` on any container that also holds an absolutely-positioned dropdown/popover is a clipping risk waiting to trigger the moment that dropdown's row is near the container's edge — check for this pattern (`overflowX` + nested `position:'absolute'` menu) before assuming a z-index bump will fix a "menu disappears" report.**
- [2026-08-24] **`AdminShell`/`AdminSidebar`'s outer flex wrapper deliberately sets `direction: 'ltr'`** (so the sidebar-right/content-left layout works via plain flex order, not RTL flipping) — but that means any new `/admin/*` page must set its own `direction: 'rtl'` on its own root content div, or all its Hebrew text silently renders left-aligned (confirmed live via screenshot on a freshly-built page that forgot this — `admin/reports/page.tsx`'s `pageWrapper` already does this correctly, it's not automatic). - [2026-08-24] **A `color: '#fff'` (or any light/white text color) hardcoded inline in this app is a strong signal of a copy-paste-from-a-dark-surface bug, not a deliberate choice** — found 6 real instances in `[stationId]/page.tsx`'s station-settings modal (payment-method checkbox labels) rendering literally invisible white-on-white against the modal's `#ffffff` background (`styles.modal`) — user reported as "לא מסתדר עם ניגודיות" without knowing the exact cause. - [2026-08-25, RESOLVED same session, bug-275] **A `{ maxWidth: 'Npx', margin: '0 auto' }` centering block placed on a direct child of a `display:'flex', flexDirection:'column'` wrapper silently shrinks to content width instead of stretching to `maxWidth`, on desktop.** Root cause is CSS Flexbox spec, not a typo: horizontal auto-margins on a flex item (cross axis, for a column flex parent) disable stretch alignment even when `align-items` is left at its default/`normal` (which otherwise behaves as `stretch`) — the item falls back to shrink-to-fit sizing. - [2026-08-24] **A CSS `rem` unit is always relative to the root `<html>` element's font-size — there is no way to locally "reset" that for a subtree; only `em` is relative to a nearby ancestor.** Built `AccessibilityWidget.tsx`'s own font-size stepper by setting `html { font-size: % }`, which correctly scales the rest of the app (most of it uses Tailwind's rem-based `text-*`/spacing utilities) — but the widget's own panel *also* used ordinary Tailwind rem-based classes (`w-72`, `text-sm`, `p-4`, etc.), so growing the page's text also grew the widget controlling it, overflowing the screen (worse on mobile — the panel got pushed above the top edge). User reported this live (bug-250). - [2026-07-02] After fixing login_log, user delete STILL 500'd. User ran a manual DELETE in the Supabase table editor and got the real Postgres error verbatim: `user_roles_user_id_fkey` also has no ON DELETE CASCADE in the live DB, despite 20260405_unified_users.sql defining it that way.
